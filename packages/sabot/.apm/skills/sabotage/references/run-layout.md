# Run layout

Every path a campaign writes is derived from `scripts/run-layout.py`. No agent builds a
path by hand.

## Roots

| Path | Durability | Lifetime | Owner |
|---|---|---|---|
| `<target>/.sabot/<run-id>/` | mixed | the campaign | orchestrator |
| `<run-root>/artifacts/` | durable | outlives the run; never auto-deleted | every node |
| `<run-root>/logs/` | durable | outlives the run; never auto-deleted | every node |
| `<run-root>/preflight.json` | durable | cited by the final report | `run-preflight.py` |
| `<run-root>/.gitignore` | durable | regenerated by `run-layout.py gitignore` | `run-preflight.py` |
| `<run-root>/ephemeral/` | ephemeral | deleted by `run-teardown.py --apply` | orchestrator |
| `<run-root>/ephemeral/<node-slug>/build/` | ephemeral | per-node `CARGO_TARGET_DIR`/`GOCACHE` | one node |
| `<run-root>/ephemeral/<node-slug>/cache/` | ephemeral | tool caches | one node |
| `<run-root>/ephemeral/<node-slug>/corpora/` | ephemeral | regenerable from `references/corpora/` | one node |
| `<run-root>/ephemeral/<node-slug>/src/` | ephemeral | copied source tree | one node |
| `~/.sabot-scratch/<repo>-<run-id>-<hash>/` | ephemeral | host-side scratch outside the repo, keyed by repo and run id so two repos' `run-1` never share one | orchestrator |

Durability is readable from the path. Exactly one segment decides it: anything under
`ephemeral/` is regenerable, everything else under the run root is evidence.
`run-layout.py classify PATH --run-root DIR` is that decision, and `run-teardown.py`
deletes only what it classifies as `ephemeral`.

## Environment

`eval "$(run-layout.py env --run-root DIR --node NODE_ID)"` exports:

`SABOT_RUN_ID`, `SABOT_RUN_ROOT`, `SABOT_ARTIFACTS`, `SABOT_LOGS`, `SABOT_EPHEMERAL`,
`SABOT_HOST_SCRATCH`, `SABOT_PREFLIGHT`, `SABOT_GITIGNORE`, `SABOT_NODE`,
`SABOT_NODE_SLUG`, `SABOT_NODE_EPHEMERAL`, `SABOT_BUILD_DIR`, `SABOT_CACHE_DIR`,
`SABOT_CORPORA_DIR`, `SABOT_SRC_DIR`.

`run-layout.py paths --run-root DIR --json` returns each variable with its durability,
lifetime, and owner.

## Artifact names

`run-layout.py artifact --run-root DIR --kind KIND --node NODE_ID` is the only sanctioned
artifact name. It yields `<artifacts>/<kind>-<node-slug><ext>`.

Node ids contain `:`; filenames use `-`. `run-layout.py slug` is that mapping and it is
idempotent. `code:metadata` becomes `code-metadata`, so the recon artifact for that node is
`recon-code-metadata.md` and its rules file is `rules-code-metadata.yml`.

A producer and a consumer that slug differently produce a missing file, and a missing rules
file reads as "0 findings" rather than a STOP. Use the function.

## Isolation

Per node, never shared:

| Resource | Path or mechanism |
|---|---|
| build output | `$SABOT_BUILD_DIR` |
| tool caches | `$SABOT_CACHE_DIR` |
| corpora | `$SABOT_CORPORA_DIR` |
| source tree, when a build must write in-tree | `$SABOT_SRC_DIR`, or `run-contained.sh --copy-src` |
| container | `--rm` per invocation, with its own `/artifacts` volume |
| bead claim | one node per surface bead |

A shared `CARGO_TARGET_DIR` produced phantom compile errors: a concurrent build erased
branch-new symbols and an agent debugged an import that was never missing.

Shared read-only:

| Resource | Why sharing is safe |
|---|---|
| the container image | read-only layers |
| baked rulesets and vulnerability databases | read-only, under `/opt` and `/deps` |
| the pre-pass output | every surface cites it rather than recomputing it |
| the target mount | `-v <target>:/target:ro` |

Full per-node isolation costs each node its own disk and memory, so it bounds concurrency.
`run-preflight.py` emits `concurrency.max_parallel_nodes`, computed from the per-node
resource estimate against measured host headroom. The figure is a ceiling, not a
preference.

## Network posture

Every target-touching container runs `--network none`, which removes DNS, egress, the proxy,
and both the package and rule registries. "Local host access" means loopback inside the
container.

A tool that needs the network is NOT EXECUTED, with that as the recorded reason. It is
never zero findings and never a retry. `preflight.json` carries the posture as
`network_posture`, and the per-image tool inventory records whether each tool works offline
or depends on a baked-in database or ruleset.

## Resource caps

`run-preflight.py` estimates per-node memory and disk from observable target properties
(workspace member count, whether anything links a cdylib, lockfile size, tracked source
size) and refuses when the target does not fit the host. `estimate.per_node_mem_mb` and
`estimate.per_node_disk_mb` feed both `run-contained.sh --mem` and any node-sizing rule: a
node too large for the estimate is split, not sampled.

`run-teardown.py --check-ceiling-mb N` is the mid-run disk watch. Nothing watched a growing
target dir, and that growth filled the host volume.

`classify-failure.py` gives every caller the same verdict on a failed run. A SIGKILL during
linking, an OOM message, `No space left on device`, or a container-store
`input/output error` is an INVALID run, not a target defect and not a finding.

### The pool is one VM, and concurrency is arithmetic

Every container's `--memory` cap is drawn from one runtime pool. Measured on the reference
host: `colima list` and `docker info` agree at **8 GiB RAM, 4 vCPU, 60 GiB disk**, while the
machine underneath is far larger. `run-preflight.py` therefore reads `MemTotal` and `NCPU`
from the runtime and marks `memory.measured_from_runtime`; a figure that came from `sysctl`
instead clamps `max_parallel_nodes` to 1, because an unconfirmed pool is not an unlimited
one.

    max_parallel_nodes = floor(memory.usable_mb / estimate.per_node_mem_mb)

with `usable_mb = pool_total_mb - 1024` reserved for the VM. A campaign held 3 concurrent
nodes and read 3 as the limit; 3 was correct only because every node ran at 2048 MiB. The
node needing 6144 cannot join two of them (6144 + 2x2048 = 10 GiB > 8 GiB), and dispatching
past that line does not run slower. The kernel OOM-kills a container, and the killed
container reports zero findings instead of reporting that it died.

`admit-node.py --preflight preflight.json --mem-cap MB --running-cap MB ...` enforces it and
exits 3 when the running sum would exceed the pool. It is the first consumer of
`preflight.json`. Lowering a cap to squeeze a node in is not the workaround; a node capped
below what it needs is the OOM.

`jobs` is derived the same way: `min(requested, floor(NCPU / concurrent_nodes))`, floor 1.
`-j 4` against 4 vCPUs with three containers competing is oversubscription, and two nodes
had to fall to `-j 1` to survive. The budget table's `jobs` is a solo-run ceiling.

One disk floor, not three: `run-preflight.py --min-free-mb` owns it, and the same value is
passed down to `run-contained.sh --min-free-mb`. `install-tools.sh --probe` reads the same
`df`; stacking a third threshold is how numbering drift started elsewhere.

### The retry ladder degrades the recipe before it raises the cap

1. `-j 1` with `CARGO_PROFILE_TEST_DEBUG=0`, `CARGO_PROFILE_DEV_DEBUG=0`,
   `CARGO_INCREMENTAL=0`. Measured: a build SIGKILLed at 2048 MiB finished in 2m47s at
   **739 MiB** under this recipe. The cap was never the fix.
2. Only if the degraded recipe still dies, one raise of `--memory` to a computed size,
   recorded as an explicit budget deviation.

Never in the ladder: `RUSTFLAGS=-Wl,--no-keep-memory`. rustc parses it as `-W l,...` and
emits E0602 on every crate, turning an OOM into a total build failure.

Disk doesn't escalate at all: the sequence is stop, report, `run-teardown.py --apply`,
verify headroom, resume. Container-store corruption is never retried. Whatever a resource
abort leaves behind is an outstanding teardown item.

Time is not a safety limit. `run-preflight.py --deadline-s` is optional and absent by
default; when set, the container stops itself at the deadline and reports the findings
collected so far, naming what had not yet run.

## Git

`<run-root>/.gitignore` is generated by `run-layout.py gitignore`. Git applies a
`.gitignore` to its own directory's subtree, so the run root holds its own file and the
target repo's `.gitignore` is untouched.

- `ephemeral/` is ignored. Multi-GiB build output cannot be swept into a commit by
  `git add .`.
- `artifacts/`, `logs/`, and `preflight.json` stay out of the ignore file. They remain untracked and
  visible in `git status`, so the user can choose to commit findings. The skill leaves them
  uncommitted and listed; committing is the user's call.

Adding an ignore rule for a durable path hides evidence.
